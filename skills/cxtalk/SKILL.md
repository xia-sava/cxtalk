# cxtalk

別のセッションと直接やりとりするためのツール。
人間が両者の間に立って伝言を運ぶ手間をなくす。

## 使う場面

開く価値があるのは、**相手の答えがないと自分の側を決められない**とき。

- 相手側の実装や制約を知らないと判断できない
- 双方の見解を突き合わせないと選べない
- 同じ話題で人間が何度も伝言している

開かなくてよいのは次の場合。

- 自分の側だけで決められる
- 伝えるだけで応答が要らない
- 相手のコードを読めば分かる

ルームを開くと人間に参加を依頼することになる。
自分の判断だけで開かず、ユーザーの依頼があるか、
ユーザーに提案して同意を得てから開く。

## 進め方

すべてのコマンドが `next` を返す。**次の行動は `next` に従う。**

| next | すること |
|---|---|
| `say` | 発言する |
| `receive` | 相手を待つ |
| `report` | 会話を終えて要約をユーザーに報告する |
| `ask_user` | ユーザーに尋ねる |

`hint` に具体的な行動が書いてある。判断に迷ったら `hint` を読む。

`ok: false` でも実行の失敗ではない。`next` が次の手を示しているので、
独自の回復動作を始めず、示されたとおりに進める。

## コマンド

```
cxtalk open    --topic <text> [--max-hops 5] [--as <name>]
cxtalk join    <room_id> [--as <name>]
cxtalk say     <room_id> --text <text> --advanced <true|false> [--as <name>]
cxtalk receive <room_id> [--timeout 100] [--as <name>]
cxtalk status  <room_id> [--as <name>]
cxtalk close   <room_id> [--reason <text>]
cxtalk ls
```

`--timeout` は既定のまま使う。100 秒は呼び出し側の制限に収まる値として選ばれており、
延ばすと外側から打ち切られて原因の分かりにくい失敗になる。
長考にはリトライで対応する。

`check` というサブコマンドもあるが、これは Stop hook が使う。自分から呼ぶ必要はない。

### 名乗り

`--as` を省略すると作業ディレクトリの名前を名乗る。通常はこれでよい。

同じディレクトリで複数のセッションを動かす場合だけ、`--as` で名乗り分ける。
**その場合は `--as` を受けるコマンドすべてに付ける。** 一つでも省くと作業ディレクトリの名前に戻り、
同名の参加者が既にいれば再入場として扱われる。
参加者が 1 人だけのルームができ、発言権が相手に渡らないまま進む。
エラーにはならないため、失敗に気づきにくい。

`cxtalk status <room_id>` の `participants` に 2 人並んでいるかで確認できる。

## 開く

```
cxtalk open --topic "<論点>"
```

`--topic` は**一つの論点に絞る**。
「認証まわり全般」ではなく「トークンの有効期限をどちらが持つか」。
広いままだと往復が発散し、上限に達しても何も決まらない。

開いた直後は `next: ask_user` が返る。相手はまだ room_id を知らないため、
ユーザーに「相手のセッションで `cxtalk join <room_id>` を実行してほしい」と依頼する。
相手の参加を確認してから第一声を送る。

往復の上限は既定で 5。短い確認なら `--max-hops 3` のように絞る。

## 参加する

```
cxtalk join <room_id>
```

`messages` に未読が入って返る。読んでから `next` に従う。

ターンが切れたあと再び会話に戻るときも同じコマンドを使う。
二度目以降は前回の続きだけが返る。

## 発言する

```
cxtalk say <room_id> --text "<本文>" --advanced <true|false>
```

本文に載せること。

- 自分の側の制約と、そう考える理由
- 相手に判断してほしい点
- 選択肢があるなら、それぞれの利害

載せないこと。

- 相手が自分のコードを読めば分かること
- 長い引用。要点を自分の言葉で書く
- 決定の宣言。決めるのは人間

### --advanced の判断

`--advanced` は「この発言で論点が前に進んだか」の自己申告。
楽観的に倒れやすいので、**迷ったら false** にする。

`false` にするもの。

- 同意・お礼・要約・確認だけの発言
- 相手の発言を言い換えただけ
- 「検討します」「確認します」で終わる発言

`true` にするもの。

- 相手が知らない制約や事実を出した
- 選択肢を絞った、または新しい選択肢を出した
- 対立点がどこにあるかを明確にした

`false` が 2 回続くとルームは自動的に閉じる。
中身のない応酬で往復を使い切らないための仕組みで、閉じられたら素直に報告に移る。

## 待つ

```
cxtalk receive <room_id>
```

相手が発言するまで戻らない。

時間切れになると `status: timeout` と `retries_left` が返る。
**これは異常ではなく通常の経路。** 長文を書く相手は 100 秒を普通に超えるため、
待機のたびに一定の割合で起きる。残り回数がある限り呼び直す。
応答がないからといって、勝手に会話を打ち切ったり自分だけで結論を出したりしない。

待機の上限に達すると `no_response` で閉じる。このとき相手が停止したのか
まだ考えているのかは区別できない。どちらかに断定せず、
応答が得られなかったという事実として報告する。

自分に発言権があるときは待たずに返る。その場合は `say` に進む。

状態だけを確認したいときは `cxtalk status <room_id>` を使う。
これは既読にならないため、未読を取りこぼさない。
開いているルームの一覧は `cxtalk ls`。

## 閉じて報告する

`next: report` が返ったら会話は終わり。ユーザーに次を報告する。

- 合意できた点
- 合意できなかった点と、双方がそう考える理由
- 持ち帰る宿題
- `log_path` が指す原文の場所

**要約には必ず `log_path` を添える。** 要約を書くのは自分であり、
自分に都合よく丸めていないことを人間が検証できる必要がある。
全発言は 1 発言 1 ファイルとしてそこに残っている。

`next: report` の出力に `messages` が付いていることがある。
往復の上限に達したとき、相手の最後の発言が未読のまま残るため。
**要約する前に必ず読む。** 相手の最終見解を読まずにまとめない。

途中で打ち切るときは `cxtalk close <room_id>`。
相手側にも終了が伝わる。

## 守ること

**ルームは論点を詰める場であり、決定する場ではない。**
成果物は「決定」ではなく「整理された論点と、双方の見解」とする。

会話で出た結論をそのまま実装しない。ユーザーに報告し、承認を得てから動く。

人間が席を外している間も往復は進む。そのことを踏まえて振る舞う。

- 相手の発言を鵜呑みにしない。自分の側の制約と食い違うなら、その場で指摘する
- 埋まらない対立を往復で押し切ろうとしない。
  二人の間で決められないと分かった時点で、対立したまま持ち帰る
- 最後の発言で押し切らない。上限に達する発言に相手は反論できない。
  hint が「相手は応答できません」と告げたら、
  合意していない点を合意したことにせず、対立を対立のまま書く
- 相手に何かを約束しない。実装するかどうかはユーザーが決める
