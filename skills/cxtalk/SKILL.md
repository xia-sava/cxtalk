# cxtalk

別のセッションと直接やりとりするためのツール。
人間が両者の間に立って伝言を運ぶ手間をなくす。

## 使う場面

開く価値があるのは、**相手の答えがないと自分の側を決められない**とき。

- 相手側の実装や制約を知らないと判断できない
- 双方の見解を突き合わせないと選べない
- 同じ話題で人間が何度も伝言している

開かなくてよいのは次の場合。

- 自分の側だけで決められる
- 伝えるだけで応答が要らない
- 相手のコードを読めば分かる

ルームを開くと人間に参加を依頼することになる。
自分の判断だけで開かず、ユーザーの依頼があるか、
ユーザーに提案して同意を得てから開く。

## 進め方

すべてのコマンドが `next` を返す。**次の行動は `next` に従う。**

| next | すること |
|---|---|
| `say` | 発言する |
| `receive` | 相手を待つ |
| `report` | 会話を終えて要約をユーザーに報告する |
| `ask_user` | ユーザーに尋ねる |
| `retry` | 呼び出しに誤りがある。hint に従って直し、同じコマンドを呼び直す |

`retry` はユーザーに尋ねる必要がない。値を書き間違えただけなので、自分で直して呼び直す。

`hint` に具体的な行動が書いてある。判断に迷ったら `hint` を読む。

`ok: false` でも実行の失敗ではない。`next` が次の手を示しているので、
独自の回復動作を始めず、示されたとおりに進める。

次の 4 つは会話する側では直せない。**hint をそのままユーザーに渡す。**
どれも `next` は `ask_user` で、勝手に別の手を試しても状況は変わらない。

| error | 何が起きているか |
|---|---|
| `corrupt_room` | 状態ファイルか発言のファイルが読めない。hint がどのファイルの何かを名指しする |
| `unwritable` | 書き込めない。置き場所が無いか権限が足りない。hint が書こうとした先を出す |
| `invalid_home` | `CXTALK_HOME` が相対パスになっている。呼ぶ場所で置き場が変わる |
| `unexpected_failure` | 上のどれでもない失敗。hint に元の文言が入るので、そのまま渡す |

`corrupt_room` の場所は `log_path` に入っている。

**`ignored` が空でなければユーザーに知らせる。** 発言として数えなかったファイルの一覧で、
`join` と `status` が返す。関係のないファイルなら放置してよいが、
本来の発言がそこに落ちていると、会話の記録が欠けたまま進むことになる。

**`unknown_keys` も同じ扱い。** `room.json` にあるが状態として読まないキーの一覧。
古い形式の名残なら放置してよいが、ユーザーが書き換えたつもりの値がここにあると、
書き換えが効いていないまま会話が進む。`max_hops` を増やしてもらった直後は特に確かめる。

## コマンド

```
cxtalk open    --topic <text> [--max-hops 5] [--as <name>]
cxtalk join    <room_id> [--as <name>]
cxtalk say     <room_id> --text <text> --advanced <true|false> [--as <name>]
cxtalk receive <room_id> [--timeout 100] [--as <name>]
cxtalk status  <room_id> [--as <name>]
cxtalk close   <room_id> [--reason manual] [--as <name>]
cxtalk ls
```

`--timeout` は既定のまま使う。100 秒は呼び出し側の制限に収まる値として選ばれており、
延ばすと外側から打ち切られて原因の分かりにくい失敗になる。
長考にはリトライで対応する。

`--reason` は `hop_limit` / `stale` / `no_response` / `idle` / `manual` のいずれか。
自由文は受け付けない。閉じた理由は報告に載るため、決まった語で残す。
自分から打ち切るときは `manual`。省略しても `manual` になる。

`check` というサブコマンドもあるが、これは Stop hook が使う。自分から呼ぶ必要はない。

### 名乗り

`--as` を省略すると作業ディレクトリの名前を名乗る。通常はこれでよい。

同じディレクトリで複数のセッションを動かす場合だけ、`--as` で名乗り分ける。
**その場合は `--as` を受けるコマンドすべてに付ける。** 一つでも省くと作業ディレクトリの名前に戻り、
同名の参加者が既にいれば再入場として扱われる。
参加者が 1 人だけのルームができる。この状態で say を呼ぶと `alone_in_room` で断られ、
`receive` で待つよう促される。**待っても相手が来ないなら名乗りを見直す。**

`cxtalk status <room_id>` の `participants` に 2 人並んでいるかでも確認できる。

名前は 1 文字以上 64 文字以内。数字だけの名前、`.` と `..`、制御文字、
ファイル名に使えない文字（`\ / : * ? " < > |`）は使えない。
メッセージのファイル名に埋まり、発言権の判定にも使うため。

### 参加者は 2 人まで

3 人目の `join` は `room_full` で断られる。発言権は 2 者の交代として回るため、
3 人目には順番が来ない。

会話の読み書きは参加者に限られる。`receive` と `say` と `close` は、
参加していない名前で呼ぶと `not_a_participant` で断られる。
`status` と `ls` は状態の確認なので誰でも呼べるが、発言の本文は返らない。
読みたければ `join` する。

## 開く

```
cxtalk open --topic "<論点>"
```

`--topic` には**詰める範囲を具体的に書く**。
「認証まわり全般」ではなく「トークンの有効期限をどちらが持つか」。
関連する複数の件をまとめて扱ってもよいが、そのときは対象を列挙する。
範囲が曖昧なままだと往復が発散し、上限に達しても何も決まらない。

開いた直後は `next: ask_user` が返る。相手はまだ room_id を知らないため、
ユーザーに「相手のセッションで `cxtalk join <room_id>` を実行してほしい」と依頼する。

**依頼したら、そのまま `receive` を呼ぶ。** 相手が参加した時点で `your_turn` が返るので、
参加できたかをユーザーに確認する必要はない。

ただし参加を待てるのは 15 分まで。過ぎると `no_response` で閉じ、
そのあとに相手が `join` しても会話は始まらない。
**依頼するときに、15 分以内に実行してほしいことを添える。**

**往復の上限は扱う件数に合わせる。** 既定は 5。上限は 4999。
一つの判断を詰めるだけなら `--max-hops 3`、
複数の案件をまとめて扱うなら件数と同じだけ見込む。
1 件あたり 1 往復を下回ると、掘り下げる前に上限へ達する。

開いた後に上限を変えるコマンドは無い。歯止めを会話する側が動かせないようにしてある。
足りなくなったらユーザーが `room.json` を書き換える。
**書き換えられたら、理由を `say` で 1 件書く。** 相手からは条件が変わった事実しか読めず、
原文だけを後から読む人間にも経緯が残らないため。

**頼むときは値の形も添える。** `max_hops` は 1 以上 4999 以下の整数で、
`"10回"` のように書くとそのルームは全コマンドで `corrupt_room` になり、
人間が直すまで会話も終了もできなくなる。

## 参加する

```
cxtalk join <room_id>
```

`messages` に未読が入って返る。読んでから `next` に従う。

ターンが切れたあと再び会話に戻るときも同じコマンドを使う。
二度目以降は前回の続きだけが返る。

## 発言する

```
cxtalk say <room_id> --text "<本文>" --advanced <true|false>
```

本文に載せること。

- 自分の側の制約と、そう考える理由
- 相手に判断してほしい点
- 選択肢があるなら、それぞれの利害

載せないこと。

- 相手が自分のコードを読めば分かること
- 長い引用。要点を自分の言葉で書く
- 決定の宣言。決めるのは人間

### --advanced の判断

`--advanced` は「この発言で論点が前に進んだか」の自己申告。
楽観的に倒れやすいので、**迷ったら false** にする。

`false` にするもの。

- 同意・お礼・要約・確認だけの発言
- 相手の発言を言い換えただけ
- 「検討します」「確認します」で終わる発言

`true` にするもの。

- 相手が知らない制約や事実を出した
- 選択肢を絞った、または新しい選択肢を出した
- 対立点がどこにあるかを明確にした

`false` が 2 回続くとルームは自動的に閉じる。
中身のない応酬で往復を使い切らないための仕組みで、閉じられたら素直に報告に移る。
閉じたときの hint が、どの 2 件がそう申告されたかを番号で名指しする。

**受け取る `messages` にも `advanced` が付く。** 相手がその発言で論点が前に進んだと
申告したかどうかで、自分の返し方は変えない。使うのは報告のときで、
`stale` で閉じた理由をユーザーに説明する際に、どの発言がそうだったかを原文と突き合わせられる。

**会話の締めくくりは `false` でよい。** 分担の確認や着手の報告に新しい情報はなく、
そこで閉じるのは正しい終わり方になる。閉じられないように `true` と申告しない。

## 待つ

```
cxtalk receive <room_id>
```

相手が発言するまで戻らない。

時間切れになると `status: timeout` と `retries_left` が返る。
**これは異常ではなく通常の経路。** 長文を書く相手は 100 秒を普通に超えるため、
待機のたびに一定の割合で起きる。残り回数がある限り呼び直す。
応答がないからといって、勝手に会話を打ち切ったり自分だけで結論を出したりしない。

待機の上限（900 秒）に達すると `status: no_answer` と `next: ask_user` が返る。
**ルームは閉じていない。** 相手が停止したのかまだ書いているのかは区別できないので、
**ユーザーに相手のセッションがまだ動いているかを確かめてもらう。**

- 動いている → `receive` を呼び直す。待機の予算は配り直されている
- 動いていない → `close` で閉じる

ここで勝手に会話を打ち切らない。

**ただし呼び直しても 30 分の掃除は止まらない。** 掃除は最後の発言からの無音で決まり、
`receive` の時間切れでは更新されない。**待ち続けていてもルームは閉じる。**
そのとき相手が書いていた本文は `closed-` で始まるファイルに残るので、
`ignored` に出ていたらユーザーに場所を伝える。

相手が一度も参加しないまま待ち切った場合だけ `no_response` で閉じる。
このとき発言は 1 件も無い。起きていない会話について要約しない。hint が告げるとおり、
room_id が正しく伝わったかをユーザーに確かめる。

自分に発言権があるときは待たずに返る。その場合は `say` に進む。

状態だけを確認したいときは `cxtalk status <room_id>` を使う。
これは既読にならないため、未読を取りこぼさない。
**待機の残りも `retries_left` で返る。** 呼び直しの回数を見失ったらこれで確かめる。
`receive` の時間切れを待つ必要はない。

ルームの一覧は `cxtalk ls`。閉じたものも含めて返るので、各行の `status` で開閉を見る。
どのルームの話かをユーザーに尋ねるときは、`closed_reason` と `hops_used` を添える。
話し切った会話と、一言も交わさずに閉じたルームは、`status` だけでは区別が付かない。
`unreadable` に room_id が並んでいたら、そのルームは状態を読み取れない。
壊れていることが伝わる窓はここだけなので、並んでいたらユーザーに知らせる。

どちらも既読にはしないが、30 分無音のルームを掃除して閉じることはある。
確認しただけで閉じたように見えても、実際には閉じる条件を満たしていたルームで、
その結果が `status` に出ている。

## 閉じて報告する

`next: report` が返ったら会話は終わり。ユーザーに次を報告する。

- 合意できた点
- 合意できなかった点と、双方がそう考える理由
- 持ち帰る宿題
- `log_path` が指す原文の場所

**要約には必ず `log_path` を添える。** 要約を書くのは自分であり、
自分に都合よく丸めていないことを人間が検証できる必要がある。
全発言は 1 発言 1 ファイルとしてそこに残っている。

`next: report` の出力に `messages` が付いていたら、**要約する前に必ず読む。**
会話が終わる経路は複数あり、どれも相手の最後の発言が未読のまま残ることがある。
相手の最終見解を読まずにまとめない。

`status` だけは既読にしない役割なので `messages` を返さない。
未読があれば hint がそう告げるので、`receive` で読んでから要約する。

途中で打ち切るときは `cxtalk close <room_id>`。
相手側にも終了が伝わる。

## 守ること

**ルームは論点を詰める場であり、決定する場ではない。**
成果物は「決定」ではなく「整理された論点と、双方の見解」とする。

会話で出た結論をそのまま実装しない。ユーザーに報告し、承認を得てから動く。

**会話の途中でターンを終えない。** `say` を送ったら、同じターンの中で `receive` を呼び続ける。
途中経過をユーザーに報告するのは構わないが、報告して**ターンを終えてはいけない。**
止まったセッションは、未読が届いても Stop hook では起こせない。hook はターンの終わりに走るので、
ターンが来ないセッションには永久に走らない。次に動けるのは人間が話しかけたときだけになり、
その間にルームは 30 分の無音で閉じる。**相手は人間に伝言を頼むしかなくなる。**

人間が席を外している間も往復は進む。そのことを踏まえて振る舞う。

- 相手の発言を鵜呑みにしない。自分の側の制約と食い違うなら、その場で指摘する
- 埋まらない対立を往復で押し切ろうとしない。
  二人の間で決められないと分かった時点で、対立したまま持ち帰る
- 最後の発言で押し切らない。上限に達する発言に相手は反論できない。
  say を促す hint が「これが最後の発言になります」と告げたら、
  合意していない点を合意したことにせず、対立を対立のまま書く
- 相手に何かを約束しない。実装するかどうかはユーザーが決める
